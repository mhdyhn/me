# میتی — همراه تمرین و باشگاه

میتی یک برنامهٔ فارسی و راست‌به‌چپ برای برنامهٔ تمرینی، ثبت ست و استراحت، سوابق، تغذیه و ارتباط مدیر، مربی و شاگرد است. رابط وب با React/TypeScript و Vite ساخته می‌شود؛ API با Node.js و PostgreSQL یا PGlite اجرا می‌شود. رابط PWA و پوستهٔ اندروید با Capacitor وجود دارند.

> بخش‌های سلامت و توصیه‌های آن آموزشی و تقریبی‌اند، نه تشخیص یا تجویز پزشکی. اتصال واقعی به Whoop، Oura، Apple Health، Fitbod، Hinge Health یا Noom وجود ندارد؛ دکمه‌های دستگاه دادهٔ نمونه تولید می‌کنند. برآورد عضلات و ضربان برای تعیین ایمنی یا شدت تمرین کافی نیست.

## نیازمندی و اجرای محلی

Node.js نسخهٔ 22.12 یا جدیدتر و npm نسخهٔ ۱۰ یا جدیدتر لازم است.

```bash
npm ci
# ترمینال اول: حساب مدیر در اولین اجرای پایگاه داده ساخته می‌شود
ADMIN_USERNAME=owner ADMIN_PASSWORD='یک-رمز-قوی-و-غیرواقعی-برای-توسعه' npm run server
# ترمینال دوم
npm run dev
```

نشانی Vite در خروجی فرمان چاپ می‌شود. سرور توسعه درخواست‌های `/api` را به `http://127.0.0.1:8787` پروکسی می‌کند؛ `API_URL` مقصد این پروکسی را تغییر می‌دهد. مرورگر لازم نیست به localhost کاربر متصل شود. دادهٔ توسعه به‌طور پیش‌فرض در `server/data/pgdata` و کلید توسعه در `server/data/dev-secret.key` است؛ هر دو از Git خارج‌اند. `DATA_DIR` این مسیر را تغییر می‌دهد. این تنظیمات و رمز نمونه برای اینترنت یا production مناسب نیستند.

حساب مدیر از طریق `ADMIN_USERNAME` و `ADMIN_PASSWORD` فقط در اولین راه‌اندازی ساخته می‌شود؛ تغییر متغیرها رمز مدیر موجود را تغییر نمی‌دهد. علاوه بر ثبت‌نام مستقیم، مدیر همچنان مربی و مربی شاگرد می‌سازد؛ تغییر رمز موقت حساب‌های دستی در نخستین ورود لازم است. مربی اشتراک جداگانه ندارد؛ مدل فروش فعلی سهم مربی و مدیریت از فروش برنامه است، نه اشتراک مربی.

مدیر پس از ورود مثل کاربر تمرین شخصی خانه، برنامه، پیشرفت، تغذیه و تنظیمات حساب خود را می‌بیند؛ «بیشتر ← مدیریت باشگاه» مسیر مربی‌ها، شاگردها و مالی است. مربی همچنان به صفحهٔ شاگردهای خود وارد می‌شود و برنامه و پیشرفت شخصی او در «بیشتر» هستند. این تغییر نقش حساب یا مجوز اتصال شاگرد به مربی را عوض نمی‌کند. برنامه و سوابق شخصی هر حساب در محدودهٔ همان حساب و با همگام‌سازی موجود نگهداری می‌شوند. اگر نخستین بررسی برنامهٔ شخصی تمام نشده باشد، خانه نبود برنامه در سرور را قطعی اعلام نمی‌کند.

```bash
npm run build             # بررسی TypeScript و ساخت dist/
npm test                  # تست‌ها
npm run test:watch
npx playwright install chromium  # یک‌بار برای آزمون مرورگری
npm run test:responsive   # بررسی صفحه‌های واکنش‌گرا در Chromium
npm run test:pwa-offline  # پس از build، آزمون PWA ساخته‌شده در Chromium
PWA_PREVIOUS_DIST=/path/to/old/dist PWA_COMPAT_DIST=/path/to/installed/dist npm run test:pwa-upgrade  # ارتقای طبیعی؛ مسیر دوم اختیاری است
npm run test:3d-qr        # پس از build، مدل، fallback و QR دعوت در Chromium
npm run benchmark:api     # اندازه‌گیری آزمایشی با حساب ساختگی و PGlite
npm run preview           # پیش‌نمایش dist/ با پروکسی API
npm run build:offline     # تولید dist/meety-offline.html
npm run verify:offline    # بررسی ساختاری بسته؛ جای تست واقعی آفلاین را نمی‌گیرد
npm run test:offline-file # پس از build:offline، ثبت ست و بازخوانی در Chromium آفلاین
```

آزمون `test:responsive` سرور توسعهٔ جداگانه‌ای اجرا و API را شبیه‌سازی می‌کند؛ به حساب و پایگاه دادهٔ واقعی دست نمی‌زند. در صورت استفاده از Chromium نصب‌شده می‌توان مسیر آن را با `CHROMIUM_PATH` داد. آزمون `test:pwa-offline` پس از `npm run build` بارگذاری CSS، پالت و آیکون نسخهٔ تازه و حفظ دادهٔ آزمایشی مرورگر را همراه با همهٔ تصویرهای SVG، یک عکس و مدل سه‌بعدی از پیش بازشده، بازشدن مسیر آفلاین و cacheنشدن API خصوصی بررسی می‌کند. حالت `PWA_PREVIOUS_DIST` در این آزمون برای ارتقا مستقیماً `registration.update()` را فراخوانی می‌کند و به‌تنهایی اثبات ارتقای طبیعی نیست.

`test:pwa-upgrade` با build قدیمیِ واقعی و بدون فراخوانی دستی update برای کلاینت قدیمی، بازخوانی عادی، پنج حساب نمونهٔ نقش‌ها، دو زبانه و پیش‌نویس ذخیره‌نشده، حفظ localStorage/IndexedDB، خطای نصب، قطع اتصال، درخواست برنامه با بدنهٔ معلق و تلاش مجدد را می‌آزماید. با `PWA_COMPAT_DIST` اختیاری، ارتقا از نسخهٔ نصب‌شده‌ای که خود اعلان به‌روزرسانی دارد نیز با دو زبانه بررسی می‌شود. API این آزمون شبیه‌سازی‌شده است؛ موفقیت آن به‌معنای بررسی تک‌تک حساب‌های production یا دستگاه‌های واقعی نیست.

`test:3d-qr` پس از ساخت production، حرکت و مکث مدل، کاهش حرکت، خطای دریافت کد/مدل، نبود WebGL، نگاشت دقیق حرکت و رمزگشایی QR بدون درخواست خارجی را در Chromium می‌آزماید. این آزمون جای گوشی واقعی یا بررسی مربی را نمی‌گیرد.

`benchmark:api` فقط از حساب ساختگی و پایگاه دادهٔ حافظه‌ای استفاده می‌کند. مقدار `BENCH_DB_DELAY_MS` تأخیر مصنوعی هر query را تعیین می‌کند (پیش‌فرض ۸۰ میلی‌ثانیه، نه تأخیر اندازه‌گیری‌شدهٔ production) و `BENCH_RUNS` تعداد تکرار را تغییر می‌دهد. شمار query و میانهٔ زمان را برای شاگرد، فرد مستقل، مربی و مدیر چاپ می‌کند.

برای بررسی یکپارچهٔ رابط، سرور و PostgreSQL، یک دیتابیس محلی کاملاً آزمایشی آماده و `TEST_POSTGRES_URL` را فقط به آن تنظیم کنید؛ سپس `npm run test:transfer-integration` را اجرا کنید. این آزمون پس از ساخت مجدد وب، یک schema تصادفی و حساب‌های ساختگی ایجاد می‌کند، از سرور محلی و sandbox استفاده می‌کند، تعارض دفتر خوراک و برنامهٔ غذایی هفتگی را در دو مرورگر مستقل بررسی می‌کند و در پایان schema را حذف می‌کند. برای جلوگیری از اشتباه، نشانی غیرلوکال را رد می‌کند؛ بااین‌حال تونل یا دیتابیس واقعی را حتی روی localhost به آن وصل نکنید. قطع اجباری آزمون ممکن است schema آزمایشی با پیشوند `meety_transfer_e2e_` بر جا بگذارد. Chromium باید نصب باشد یا با `CHROMIUM_PATH` مشخص شود؛ هیچ پرداخت بانکی انجام نمی‌شود.

برای آزمون تکمیلی مهاجرت، نشست، فروش برنامه، خرید آزمایشی و عملیات هم‌زمان روی PostgreSQL واقعی، متغیر `TEST_POSTGRES_URL` را **فقط به یک دیتابیس آزمایشی قابل دورریختن** بدهید و `npx vitest run server/postgres-auth.test.ts server/postgres-program-sales.test.ts server/postgres-test-purchase.test.ts server/postgres-coach-invites.test.ts server/postgres-registration-migration.test.ts` را اجرا کنید. کاربر دیتابیس باید اجازهٔ ساخت schema داشته باشد؛ هر پرونده یک schema تصادفی می‌سازد و پس از اجرا حذف می‌کند. بدون این متغیر، تست‌های PostgreSQL اجرا نمی‌شوند. از نشانی production استفاده نکنید.

ساخت تک‌فایل جاوااسکریپت، CSS، فونت‌های ساخته‌شده و آیکون‌های سند را داخل HTML قرار می‌دهد و برای بازشدن با `file://` از مسیرهای هش (`#/…`) استفاده می‌کند. این نسخه جای API را نمی‌گیرد و همهٔ تصاویر و امکانات حساب‌دار را آفلاین نمی‌کند؛ نتیجه به مرورگر و مجوز حافظهٔ آن هم وابسته است. `verify:offline` فقط چند کنترل ساختاری است.

## استقرار و پیکربندی

برای نسخهٔ حساب‌دار، یک PostgreSQL پایدار و API لازم است. فایل‌های `dist/` را سرور Node یا یک میزبان ایستا با fallback مسیرهای SPA ارائه می‌کند. اگر وب و API جدا هستند، `/api` را با reverse proxy به سرور برسانید یا نشانی API را هنگام ساخت وب با `VITE_API_BASE` تنظیم کنید. در production از HTTPS و reverse proxy با کنترل `Host` استفاده کنید و `Host` اصلی را به API منتقل کنید. نصب PWA به قابلیت مرورگر و زمینهٔ امن HTTPS وابسته است.

### به‌روزرسانی وب و PWA

در نسخهٔ تازه، سرویس‌ورکر هنگام بازگشت صفحه به اینترنت، بازشدن صفحه و به‌صورت دوره‌ای بررسی می‌شود. وقتی نسخهٔ تازه آماده شود، صفحهٔ باز پیام می‌دهد؛ فقط با انتخاب و تأیید کاربر دوباره بارگذاری می‌شود، چون پیش‌نویس‌ها ممکن است هنوز ذخیره نشده باشند. در پیمایش آنلاین، فایل اصلی صفحه از سرور خوانده می‌شود و اگر سرور در دسترس نباشد، پوستهٔ ذخیره‌شده استفاده می‌شود. تعدادی فایل عمومی نسخه‌های قبلی برای کمک به زبانه‌های باز نگه داشته می‌شوند، اما ظرفیت محدود است و مرورگر ممکن است cache را پاک کند. پاسخ‌های خصوصی API در این cache قرار نمی‌گیرند.

صفحه‌های بسیار قدیمی هنوز کد نمایش پیام را ندارند و نمی‌توان بدون احتمال حذف پیش‌نویس، آن‌ها را از راه دور به‌اجبار بازخوانی کرد. روی چنین صفحه‌ای تغییرات را ذخیره کنید، با اینترنت پایدار صفحه را تازه کنید، به نصب پس‌زمینه فرصت دهید و اگر هنوز طرح قدیمی بود دوباره تازه کنید؛ اتصال کند یا شکست دانلود می‌تواند این روند را طولانی‌تر کند. اطلاعات مرورگر را برای به‌روزرسانی پاک نکنید. دستگاه آفلاین یا زبانه‌ای که هیچ‌گاه دوباره بررسی نمی‌شود، فوراً به‌روز نخواهد شد. شناسهٔ نسخهٔ رابط جاری در انتهای «تنظیمات» نمایش داده می‌شود؛ فقط اگر در زمان ساخت شناسهٔ commit معتبر وجود داشته باشد، هشت رقم اول آن دیده می‌شود و در غیر این صورت «نامشخص» است. این شناسه مربوط به کدی است که دستگاه بارگذاری کرده، نه تضمین سالم‌بودن سرور یا همهٔ حساب‌ها. APK قدیمی به‌طور مستقل باید با امضای سازگار به‌روزرسانی شود.

| متغیر | کاربرد |
|---|---|
| `NODE_ENV=production` | سیاست production؛ بدون پایگاه داده و کلید زیر سرور راه نمی‌افتد. |
| `DATABASE_URL` | اتصال PostgreSQL پایدار؛ در production اجباری. پیش از مهاجرت از دیتابیس پشتیبان بگیرید. |
| `MEETY_SECRET` | حداقل ۱۶ نویسه و برای حفاظت از اطلاعات رمزهای موقت؛ تصادفی، محرمانه و پایدار نگه دارید. تغییر یا از دست‌دادن آن می‌تواند خواندن اطلاعات رمزهای قبلی را ناممکن کند. |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD` | فقط ساخت اولیهٔ مدیر؛ مقدار واقعی را در مخزن یا لاگ قرار ندهید. |
| `HOST`, `PORT`, `STATIC_DIR` | آدرس گوش‌دادن، پورت پیش‌فرض `8787` و پوشهٔ وب پیش‌فرض `dist`. |
| `CORS_ALLOWED_ORIGINS` | مبدأهای مجاز اضافی، جداشده با ویرگول، مانند `https://app.example.com,https://admin.example.com`. مبدأ هم‌میزبان و مبدأهای محلی Capacitor نیز پذیرفته می‌شوند؛ wildcard وجود ندارد. این کنترل جای احراز هویت یا محدودسازی Host در پروکسی را نمی‌گیرد. |
| `COOKIE_SECURE` | مقدار `1` کوکی امن را خارج از production نیز فعال می‌کند؛ در production خودکار است. |
| `MEETY_TRUSTED_PROXIES` | اختیاری؛ فهرست IP یا CIDR پروکسی‌های واقعاً تأییدشده با جداکنندهٔ ویرگول. خالی یا تعریف‌نشده یعنی سربرگ‌های آدرس نادیده گرفته می‌شوند. مقدار نادرست مانع راه‌اندازی می‌شود؛ جزئیات و هشدار امنیتی پایین را ببینید. |
| `ZARINPAL_MERCHANT_ID` | شناسهٔ واقعی پذیرنده برای پرداخت production؛ بدون آن پرداخت واقعی بسته می‌ماند. هر مقدار غیرخالی، خرید آزمایشی شاگرد را غیرفعال می‌کند. |
| `STUDENT_TEST_PURCHASES` | برای بستن خرید آزمایشی مقدار `off`، `false` یا `0` بدهید. بدون این مقدار و شناسهٔ پذیرنده، امکان مجوز فردی مربی یا فعال‌سازی صریح آزمایش سراسری توسط مدیر وجود دارد؛ آزمایش سراسری به‌طور پیش‌فرض خاموش است. |
| `PAYMENT_PUBLIC_BASE_URL` | مبدأ عمومی HTTPS صفحهٔ بازگشت، بدون مسیر یا query، مثل `https://app.example.com`؛ برای شروع پرداخت در production اجباری است. |
| `ZARINPAL_SANDBOX` | مقدار `true` فقط در محیط غیر production شبیه‌ساز محلی را فعال می‌کند؛ در production موجب رد پرداخت است. در توسعه نبود merchant نیز شبیه‌ساز را فعال می‌کند. |
| `COACH_COMMISSION_PERCENT` | سهم مربی از ۰ تا ۱۰۰؛ پیش‌فرض ۹۰. تنظیم نامعتبر باعث رد عملیات می‌شود. |
| `VITE_API_BASE` | مبدأ HTTPS API اندروید/کلاینت جدا؛ در زمان **ساخت** وارد باندل می‌شود و نباید شامل اطلاعات محرمانه باشد. برای وب هم‌مبدأ خالی بماند. |
| `VITE_ANDROID_APK_URL` | نشانی HTTPS یا مسیر هم‌مبدأ APK امضاشده و بررسی‌شده؛ فقط در زمان ساخت وب تنظیم شود. بدون آن دکمهٔ دانلود APK نشان داده نمی‌شود. |

مبدأهایی که برنامه از آن‌ها API را فراخوانی می‌کند باید در پیکربندی CORS مجاز باشند؛ در صورت تغییر آدرس، سازگاری کوکی، نشست و جریان بازگشت پرداخت را در محیط staging بررسی کنید. پروکسی باید دست‌کم یکی از سربرگ‌های `Authorization` یا `X-Meety-Session` را به API برساند؛ درخواست‌های همگام‌سازی برای جلوگیری از جابه‌جایی حساب از کوکی استفاده نمی‌کنند و بدون این سربرگ‌ها بسته می‌مانند. متغیرهای `VITE_` عمومی‌اند؛ کلید یا رمز در آن‌ها قرار ندهید.

### شاخهٔ ثابت انتشار Render

شاخهٔ انتشار `main` است. تغییرات هر نشست ابتدا در شاخهٔ کاری همان نشست آزموده و سپس با درخواست ادغام (PR) به `main` منتقل می‌شوند؛ Render باید به `main` متصل و Auto-Deploy آن روی `On Commit` باشد. فایل `render.yaml` هر دو تنظیم را مشخص می‌کند، **اما فقط در صورت مدیریت سرویس با همین Blueprint و فعال‌بودن همگام‌سازی آن اعمال می‌شود**؛ فایل مخزن به‌تنهایی ثابت نمی‌کند تنظیم فعلی داشبورد چیست. برای سرویس موجودِ غیر Blueprint باید این دو مورد یک‌بار در داشبورد تنظیم شوند. فعال‌بودن Auto-Deploy هم تضمین موفقیت ساخت یا استقرار نیست؛ پس از هر انتشار، وضعیت Live و خود برنامه باید بررسی شود.

مسیر عمومی و بدون cacheِ `/api/release` فقط شاخهٔ ثابت مورد انتظار، وضعیت شاخهٔ آخرین استقرار (`main`، `other` یا `unknown`) و شناسهٔ معتبر commit در Render را نمایش می‌دهد؛ نام شاخه‌های دیگر، مقدار کلیدها و اطلاعات حساب را نشان نمی‌دهد. این خروجی از متغیرهای پیش‌فرض Render خوانده می‌شود و به‌تنهایی اتصال دائمی شاخه یا فعال‌بودن Auto-Deploy در داشبورد را اثبات نمی‌کند. خارج از Render یا در صورت نبود متغیرها، مقدار `unknown` گزارش می‌شود.

فیلد `databaseMs` در `/api/health` فقط زمان یک `SELECT 1` از دید سرور را نشان می‌دهد؛ زمان شبکهٔ کاربر، ورود، دریافت برنامه، بارگذاری صفحه و بیدارشدن کامل سرویس نیست. فایل Blueprint طرح رایگان را پیشنهاد می‌کند ولی وضعیت واقعی سرویس باید در داشبورد بررسی شود. طبق [راهنمای Render](https://render.com/docs/free)، اگر سرویس واقعاً رایگان باشد، پس از ۱۵ دقیقه بی‌ترافیکی می‌خوابد و بیدارشدن ممکن است حدود یک دقیقه طول بکشد؛ بهینه‌سازی query جای سرویس همیشه‌روشن را نمی‌گیرد.

در ساخت وب، تصویرهای SVG تمرین برای PWA در یک بستهٔ عمومی precache می‌شوند؛ پس از نصب کامل، آن‌ها آفلاین در دسترس‌اند. عکس‌ها و فایل‌های نمای سه‌بعدی فقط پس از اولین دریافت در cache عمومی ذخیره می‌شوند؛ پاسخ‌های API خصوصی cache نمی‌شوند. بستهٔ تک‌فایل آفلاین مدل سه‌بعدی را در خود ندارد. این آزمایش‌ها اثبات آفلاین‌بودن همهٔ گردش‌های برنامه یا همگام‌سازی نیستند. `npm run build` نسخهٔ gzip دارایی‌های عمومی مناسب از جمله مدل را می‌سازد و سرور Node با `Content-Encoding` و `Vary` درست، در صورت پشتیبانی مرورگر آن را ارسال می‌کند. میزبان ایستای مستقل باید فشرده‌سازی و fallback مناسب را خودش پیکربندی کند.

### نمای تمرین و دعوت مربی

- پوستهٔ فارسی و RTL با پس‌زمینهٔ سرمه‌ای، سطح‌های آبی و تأکید فیروزه‌ای طراحی شده است؛ اثر روان‌شناختی رنگ به زمینه و فرد بستگی دارد و وعدهٔ قطعی انگیزه یا اعتماد نیست. کنتراست ۱۲ صفحهٔ نمونه با axe در Chromium بررسی شده، نه همهٔ حالت‌ها و نه انطباق کامل دسترس‌پذیری.
- نمایشگر مدل متحرک فقط برای شناسهٔ دقیق `push-up` (شنا سوئدی) و با درخواست کاربر دریافت می‌شود؛ تغییر زاویه، مکث و حالت کاهش حرکت دارد و در خطای دریافت یا نبود WebGL راهنمای تصویری قبلی باقی می‌ماند. حجم مدل حدود ۸۸۰ کیلوبایت خام و ۴۲۳ کیلوبایت gzip است و کد نمایش نیز جداگانه دریافت می‌شود؛ کارایی روی گوشی واقعی و دقت آناتومیک توسط متخصص تأیید نشده‌اند. برای سایر حرکات مدل سه‌بعدی وجود ندارد. منشأ و مجوز مدل در `public/models/NOTICE.md` است.
- شناسهٔ موجود `swedish-dip` نیز در برنامه‌ها «شنا سوئدی» نام دارد، اما راهنمای آن dip روی میلهٔ موازی را توصیف می‌کند؛ برای جلوگیری از راهنمای اشتباه، مدل شنا به آن متصل نشده و معنا یا نام برنامه‌های کاربران تغییر نکرده است. پیش از اصلاح داده باید مربی حرکت واقعی را تأیید کند.
- مربی از «لینک ثبت‌نام شاگرد» یک لینک اختصاصی برای چند شاگرد دریافت و کپی می‌کند یا QR همان لینک را به‌صورت محلی نمایش می‌دهد؛ تصویر به سرویس خارجی فرستاده نمی‌شود. لینک تا زمان غیرفعال‌کردن معتبر است. بعد از غیرفعال‌سازی، لینک تازه متفاوت است و شاگردان متصل یا اطلاعاتشان تغییر نمی‌کنند. مالک لینک می‌تواند نام مربی را ببیند، پس آن را فقط در جای مناسب منتشر کنید؛ بازکردن لینک به‌تنهایی کسی را متصل نمی‌کند. اسکنر داخلی وجود ندارد.
- امکان صدور و ابطال کدهای محرمانهٔ قدیمی یک‌بارمصرف در بخش جمع‌شونده همچنان باقی است؛ هر کد حداکثر ۴۸ ساعت اعتبار دارد و صدور کد تازه الزماً قبلی‌ها را لغو نمی‌کند. QR نمایش‌داده‌شده در مسیر اصلی مخصوص لینک ثبت‌نام است، نه کد خام قدیمی.

### ثبت‌نام، حساب مستقل و دعوت مربی

- شاگرد می‌تواند بدون مربی ثبت‌نام کند و امکانات پایهٔ موجود را با حساب خود استفاده و میان دستگاه‌ها همگام کند. مربی هم ثبت‌نام می‌کند، اما تا تأیید مدیر ورودش فعال نمی‌شود. مدیر همهٔ مربیان و شاگردان، از جمله حساب‌های مستقیم و دستی را می‌بیند و امکان فعال/غیرفعال‌کردن و بازنشانی رمز را دارد. مربی نمی‌تواند رمز یا وضعیت حسابی را که شاگرد خودش ساخته تغییر دهد یا آن را حذف کند. قبل از بازنشانی رمز باید هویت صاحب حساب خارج از برنامه بررسی شود؛ بازیابی خودکار وجود ندارد.
- نام، نام کاربری، رمز و شماره موبایل ایران برای ثبت‌نام جدید لازم‌اند؛ در ساخت دستی نام کاربری و رمز موقت خودکار ساخته می‌شوند و نام و شماره لازم است. ارقام فارسی/عربی و پیش‌شمارهٔ ایران پذیرفته و به قالب `09xxxxxxxxx` تبدیل می‌شوند. شماره **با پیامک تأیید نمی‌شود** و یکتا نیست؛ مالکیت آن احراز نشده است. حساب‌های قدیمی بدون شماره باقی می‌مانند و شماره‌شان «ثبت نشده» نمایش داده می‌شود. مدیر و مربیِ متصل شماره را در مسیرهای مجاز می‌بینند.
- شاگرد لینک اختصاصی مربی را باز می‌کند، حساب مستقل می‌سازد یا وارد حساب خود می‌شود، نام مربی و دسترسی به نام، شماره، خلاصهٔ تمرین، دفتر خوراک و مدیریت برنامه را می‌بیند و جداگانه قبول می‌کند. اشتراک پروفایل رضایت جداگانه دارد. کد یک‌بارمصرف قدیمی نیز همچنان پشتیبانی می‌شود. پس از قطع دسترسی، شاگرد خودثبت‌نام‌کرده می‌تواند برنامهٔ شخصی‌اش را فعال کند یا با لینک یا کد معتبر به مربی وصل شود. برای حساب شاگردِ ساخته‌شده توسط مربی، تغییر مربی خودخدمت هنوز طراحی نشده است.
- جدول افزایشی `coach_registration_links` برای لینک معرفی در startup ساخته می‌شود؛ حساب‌ها و کدهای قبلی بازنویسی نمی‌شوند. متن توکن در جدول ذخیره نمی‌شود؛ nonce و هش کلیددار ذخیره و توکن با `MEETY_SECRET` بازتولید می‌شود. تغییر کلید، لینک‌های قبلی را نامعتبر می‌کند. توکن در بخش fragment نشانی قرار دارد، سپس برای ادامهٔ ثبت‌نام/ورود در حافظهٔ همان زبانه و وضعیت مسیریابی نگه داشته می‌شود؛ نسخهٔ sessionStorage پس از اتصال پاک می‌شود، ولی ممکن است در تاریخچهٔ همان زبانه باقی بماند و در برابر اسکریپت‌های همان مبدأ محرمانه نیست. برای پیش‌نمایش سهمیه وجود دارد و تا تأیید زنجیرهٔ پروکسی واقعی ممکن است سهمیه بین کاربران مشترک شود.
- انتخاب تاریخ وزن، دفتر وعدهٔ شاگرد و مشاهدهٔ دفتر توسط مربی با سال، ماه و روز شمسی انجام می‌شود؛ کلید تاریخ و قرارداد سرور همچنان `YYYY-MM-DD` میلادی هستند. دریافت شبا رقم فارسی و عربی را به انگلیسی تبدیل می‌کند؛ اعتبارسنجی کنونی فقط قالب `IR` و ۲۴ رقم را بررسی می‌کند، نه checksum، مالکیت یا تأیید بانکی.
- خریدهای واقعی و برنامه‌های رایگان قبلی در بایگانی فقط‌خواندنی شاگرد می‌مانند؛ خرید آزمایشی فقط تا پایان مجوز قابل مشاهده است. برنامهٔ غذایی، تنظیمات پایش و گفتگوی هر مربی از مربی دیگر جداست؛ خود شاگرد به بایگانی دسترسی دارد و در گفتگو ۲۰۰ پیام آخر نمایش داده می‌شود. مربیِ متصل می‌تواند برنامهٔ سابق خودش را با همان شناسه فعال و برای خریدار قبلی رایگان ویرایش کند. خلاصهٔ تمرین‌ها و دفتر خوراک با رضایت اتصال برای مربی جدید قابل مشاهده‌اند؛ اشتراک پروفایل باید جداگانه تأیید شود.
- قطع دسترسی می‌تواند فوری انجام شود، ولی تغییر برنامه/اتصال تا پایان و همگام‌سازی تمرین فعال مسدود است؛ تمرین آفلاین دستگاه دیگر ممکن است هنوز به سرور نرسیده باشد. درخواست‌های خواندنِ آغازشده پیش از قطع ممکن است کامل شوند؛ نوشتن‌های محافظت‌شده پس از تغییر رابطه با نسخهٔ قدیمی رد می‌شوند. درخواست بی‌پاسخ را پس از بررسی وضعیت حساب تکرار کنید.
- برای جلسه‌های تازهٔ شخصی، رایگان و خریداری‌شده نسخهٔ برنامهٔ شروع در خود جلسه ثبت می‌شود تا با حذف یا تغییر برنامه، تمرین و نام حرکت‌های قبلی اشتباه نشوند. برای خرید آزمایشی فقط شناسه و نسخهٔ پیشنهاد ذخیره می‌شود؛ ادامه نیازمند همان نسخه و مجوز معتبر است. جلسهٔ قدیمی بدون نسخهٔ ذخیره‌شده حتی با نام و حرکت‌های مشابه قابل بازسازی قطعی نیست: ادامهٔ خودکار متوقف می‌شود، اما می‌توان جلسه را با ست‌های موجود بست. هنگام آغاز، دریافت اولیهٔ اطلاعات دستگاه‌های دیگر انتظار کشیده می‌شود؛ در آفلاین ممکن است جلسهٔ دیگر هنوز دیده نشود و پس از همگام‌سازی، چند جلسهٔ فعال برای بررسی و بستن بدون حذف ست‌ها نمایش داده می‌شود.
- برای حفظ گزارش مالی و گفتگوی مربی سابق، حسابی که به این سوابق یا داده‌های وابسته مرتبط است حذف نمی‌شود و می‌توان آن را غیرفعال کرد. حذف صریح شاگرد دستیِ بدون تراکنش همچنان می‌تواند داده‌ها و گفتگوی آن شاگرد را پاک کند؛ حسابی که شاگرد خودش ثبت کرده به دست مربی حذف نمی‌شود. این رفتار جای سیاست کامل درخواست حذف حساب، نگهداری قانونی یا بازیابی داده را نمی‌گیرد.
- مهاجرت، داده‌های تغذیه و پایش را بر اساس مربی جدا می‌کند. پایش قدیمیِ ثبت‌شده توسط مدیر به مربی فعلی شاگرد در زمان مهاجرت نسبت داده می‌شود؛ این فرض برای داده‌های دست‌کاری‌شده یا انتقال‌های خارج از برنامه ممکن است نادرست باشد و باید روی کپی داده بررسی شود. برنامه‌ها و اطلاعاتی که در نسخه‌های قدیمی قبلاً حذف شده‌اند خودکار بازسازی نمی‌شوند. راهنمای پشتیبان، بررسی داده و بازگشت پایین ضروری است.

### محدودیت ثبت‌نام پشت پروکسی

محدودیت ثبت‌نام در PostgreSQL نگهداری می‌شود: حداکثر ۳۰ درخواست از هر مبدأ و ۱۰۰ درخواست سراسری در هر ۱۵ دقیقه. به‌طور پیش‌فرض فقط IP اتصال مستقیم ملاک است و هیچ `X-Forwarded-For` ارسالی از مرورگر پذیرفته نمی‌شود؛ اگر همه از یک پروکسی عبور کنند، کاربران ممکن است سهمیهٔ ۳۰تایی مشترک داشته باشند. حتی با شناسایی درست IP، سقف سراسری ۱۰۰ درخواست تغییری نمی‌کند و برای جذب انبوه باید ظرفیت و محافظت ضدسوءاستفاده بازطراحی شوند.

`MEETY_TRUSTED_PROXIES` فقط پس از تأیید مسیر واقعی ingress، مسدودبودن دسترسی مستقیم به API و شیوهٔ بازنویسی/افزودن `X-Forwarded-For` در **تمام hopها** قابل تنظیم است. فقط IP/CIDR دقیق پروکسی‌های تحت کنترل را، با ویرگول، وارد کنید؛ resolver زنجیره را از سمت سرور تا نخستین hop غیرقابل‌اعتماد طی می‌کند. اعتماد به شبکهٔ بیش‌ازحد گسترده یا پروکسی‌ای که سربرگ مهاجم را بدون کنترل می‌پذیرد می‌تواند محدودیت را دور بزند. هیچ IP یا محدوده‌ای برای Render در این مخزن تأیید نشده؛ آن را حدسی فعال نکنید. قبل از تغییر، از چند مبدأ واقعی و با سربرگ ساختگی و مسیر مستقیم آزمایش کنید. این تنظیم عمومی Node/پروکسی است، نه اثبات حل مشکل Render.

### پشتیبان، آزمون مهاجرت و بازگشت

لینک ثبت‌نام این نسخه یک جدول افزایشی در startup می‌سازد. آزمون آن روی PostgreSQL دورریختنی موفق بوده، نه روی کپی دادهٔ واقعی؛ پیش از استقرار، پشتیبان تازه و بازیابی‌شده و آزمون مهاجرت روی کپی جداگانه را تأیید کنید. تأیید مربوط به انتشارهای قبلی به‌تنهایی برای این انتشار کافی نیست.

این برنامه در راه‌اندازی پایگاه داده را خودکار مهاجرت می‌دهد. مهاجرت فعلی جدول‌های جدا برای داده‌های مربیان، محافظت از حذف آبشاری گفتگو/تراکنش، و ستون‌های نسخهٔ `BIGINT` می‌سازد؛ فعال‌سازی مجدد برنامهٔ بایگانی‌شده از نسخهٔ ۲٬۱۴۷٬۴۸۳٬۶۴۸ یا بیشتر استفاده می‌کند. نسخهٔ قدیمی سرور و ستون‌های ۳۲بیتی با این وضعیت و رابطهٔ جدید سازگار نیستند. **پیش از اتصال این نسخه به دادهٔ واقعی، پشتیبان سالم، بازیابی آزمایشی و اجرای مهاجرت روی کپیِ جدا لازم است؛ آزمایش دیتابیس ساختگی محلی جای آن‌ها نیست.**

۱. از ابزار رسمی PostgreSQL متناسب با نسخهٔ سرور استفاده کنید؛ `pg_dump` نباید از سرور قدیمی‌تر باشد و `pg_restore` و مقصد باید با dump سازگار باشند. مجوز، گواهی TLS و ظرفیت مقصد را بررسی کنید. برای دوری از قرارگرفتن گذرواژه در خط فرمان، از سرویس‌های محرمانهٔ libpq و فایل مجوز محدود مانند `PGSERVICE`/`.pgpass` استفاده کنید؛ اطلاعات اتصال، `MEETY_SECRET`، شماره‌ها و dump را در Git، لاگ یا گفتگو قرار ندهید.
۲. در محیط عملیاتی امن و با مجوز مناسب، از PostgreSQL واقعی یک dump منطقی با فرمت custom بگیرید، آن را رمزگذاری و خارج از سرویس اصلی با کنترل دسترسی و سیاست نگهداری نگه دارید. نمونهٔ فرمان زیر به سرویس‌های libpq از پیش‌پیکربندی‌شده و مقصد خالیِ دورریختنی اشاره می‌کند، نه به خود production:

```bash
umask 077
# PGSERVICEها و BACKUP_FILE/RESTORE_DATABASE_NAME را خارج از مخزن و بدون چاپ اطلاعات محرمانه تنظیم کنید.
PGSERVICE=meety_backup pg_dump --format=custom --no-owner --no-acl --file="$BACKUP_FILE"
pg_restore --list "$BACKUP_FILE" >/dev/null
PGSERVICE=meety_disposable_restore pg_restore --exit-on-error --no-owner --no-acl --dbname="$RESTORE_DATABASE_NAME" "$BACKUP_FILE"
```

۳. مقصد بازیابی باید واقعاً جدا، خالی و قابل حذف باشد؛ آدرس آن را پیش از اجرای restore دو بار بررسی کنید. پس از بازیابی، تطبیق شمارش و نمونه‌های مجاز حساب، برنامه، تراکنش، تغذیه، پایش، گفتگو، دادهٔ شخصی و sequenceها را با فرد مجاز انجام دهید؛ سپس مهاجرت را روی همان کپی اجرا و دوباره بررسی کنید. فقط فهرست‌کردن dump، امکان بازیابی یا صحت محتوا را اثبات نمی‌کند. dump بالا نقش‌های سراسری، مجوزها، متغیرهای محیطی، کلیدها و تغییرات آفلاینِ هنوز همگام‌نشده را نگه نمی‌دارد؛ برنامهٔ جداگانهٔ امن برای آن‌ها لازم است. پشتیبان کلید پایدار `MEETY_SECRET` جداگانه و محرمانه نگهداری شود.
۴. پیش از انتشار، با هماهنگی و اطلاع کاربران نوشتن و فروش را متوقف، درخواست‌ها و callbackهای در حال انجام را تعیین‌تکلیف، دستگاه‌ها را همگام و پشتیبان تازه و بازیابی‌شده را تأیید کنید. از اجرای هم‌زمان سرور قدیم و جدید روی یک دیتابیس پرهیز کنید؛ کلاینت قدیمی برای ویرایش/حذف و شروع خرید ممکن است نیاز به تازه‌سازی داشته باشد. سلامت، نسخهٔ استقرار، سه نقش و وضعیت خریدهای در انتظار را پس از استقرار بررسی کنید.
۵. بازگشت سادهٔ کد یا تبدیل `BIGINT` به `INTEGER` امن نیست. ترجیح، رفع رو به جلو است؛ در صورت ضرورت بازگشت، ابتدا فروش و نوشتن را متوقف و اثر تفاوت رابطه‌ها، نسخه‌ها و تراکنش‌ها را با پشتیبان و مسئول داده بررسی کنید. بازگرداندن dump پیش از مهاجرت می‌تواند تغییرات بعد از زمان dump را از دست بدهد و نیاز به تصمیم و طرح تطبیق جداگانه دارد. آزمون بازگشت باید روی کپی و با زمان‌بندی قابل قبول انجام شود.

پیش از مهاجرت روی کپی، ردیف‌هایی را که `student_programs.coach_id` با مربی فعلی شاگرد متفاوت است و نیز رکوردهای قدیمی پایش با ویرایشگر مدیر بررسی کنید؛ ممکن است ناشی از دادهٔ قدیمی یا تغییر خارج از برنامه باشد و انتساب مالکیت از روی نام قابل حدس نیست. گزارش را نزد فرد مجاز و محرمانه نگه دارید. طرح واقعی سرویس پایگاه داده و قابلیت PITR/backup میزبان را از داشبورد بررسی کنید؛ `render.yaml` وجود پشتیبان خودکار یا آزمون‌شده را تضمین نمی‌کند.

### نشست و انتشار امن

- تغییر رمز توسط کاربر، نشست همین دستگاه را حفظ و سایر نشست‌های همان حساب را باطل می‌کند. بازنشانی رمز توسط مربی/مدیر و غیرفعال‌کردن حساب همهٔ نشست‌های آن حساب را باطل می‌کند؛ پس از فعال‌سازی مجدد، ورود دوباره لازم است. ابطال برای درخواست‌های بعدی است و درخواست از قبل احراز‌شده ممکن است تمام شود. داده‌های ذخیره‌شدهٔ محلی حذف نمی‌شوند، اما دستگاه آفلاین تا اتصال مجدد از ابطال مطلع نمی‌شود. توکن نشست فعلی هنگام تغییر رمز عوض نمی‌شود؛ اگر احتمال کپی‌شدن همان توکن وجود دارد، هنگام اتصال از حساب خارج شوید و دوباره وارد شوید، یا از مسئول حساب بازنشانی رمز بخواهید. خروج محلی در حالت قطع ارتباط ابطال سروری را تضمین نمی‌کند.
- مهاجرت دو ستون نسخه به جدول‌های کاربر و نشست اضافه می‌کند؛ نشست‌های معتبر قبلی در مهاجرت اولیه حفظ می‌شوند. پیش از استقرار از PostgreSQL پشتیبان بگیرید و مهاجرت و ورود را در staging آزمایش کنید. سرور قدیمی نسخهٔ نشست را بررسی نمی‌کند؛ در استقرار چندنمونه‌ای از سرو هم‌زمان نسخه‌های قدیم و جدید پرهیز کنید. برای بازگشت به سرور قدیمی، پیشاپیش با اطلاع کاربران برنامهٔ ابطال همهٔ نشست‌های ورود را اجرا کنید.
- محدودیت تلاش ورود در حافظهٔ همان فرایند است و میان چند نمونه مشترک نیست؛ جای محدودسازی توزیع‌شده و محافظت در لایهٔ پروکسی را نمی‌گیرد. تلاش‌های ناقص نیز پس از پنجرهٔ عدم فعالیت پاک می‌شوند.
- هنگام ذخیرهٔ برنامهٔ شاگرد توسط مدیر، شناسهٔ مربیِ اختصاص‌یافته ثبت می‌شود. رکوردهای قبلی خودکار بازنویسی نشده‌اند؛ در صورت نیاز، اصلاح آن‌ها پس از بررسی و پشتیبان‌گیری جداگانه انجام شود.

### پرداخت

درگاه واقعی در production در صورت نبود پیکربندی، خطای شبکه یا پاسخ نامعتبر **به شبیه‌ساز تغییر نمی‌کند**. تأیید باید از سمت درگاه و همراه شناسهٔ پیگیری باشد؛ تراکنش‌های sandbox و شناسه‌های پیگیری نامعتبر قدیمی به دسترسی production تبدیل نمی‌شوند. سوابق واقعی قدیمی بدون شناسهٔ قابل قبول نیاز به بررسی پشتیبانی دارند. خواندن یا تأیید تراکنش حساب‌دار به شاگرد صاحب تراکنش، مربی مربوط و مدیر محدود است.

پیش از اتصال درگاه، مربی یا مدیر در صفحهٔ تراکنش‌ها می‌تواند «آزمایش پرداخت بدون درگاه» را با مبلغ نمونه اجرا کند؛ برنامه‌ساز نیز تمرین نمایشی مبلغ برنامهٔ ذخیره‌شده را دارد. این تمرین فقط پیش‌نمایش است و برنامه را باز نمی‌کند، تراکنش و درآمد نمی‌سازد و به زرین‌پال یا نشانی بازگشت متصل نمی‌شود.

**خرید آزمایشی با گزارش مالی، جدا از پیش‌نمایش:** در نبود `ZARINPAL_MERCHANT_ID` غیرخالی و با روشن‌بودن قابلیت در سرور، ابتدا مربی یک برنامهٔ پولی ذخیره می‌کند. مدیر در «تراکنش‌های کل باشگاه» می‌تواند پس از خواندن هشدار، «فعال‌کردن آزمایش سراسری» را تأیید کند. این حالت حداکثر ۲۴ ساعت روشن است و در این مدت **همهٔ شاگردان می‌توانند برنامهٔ پولی فعال خود را بدون پرداخت بانکی آزمایشی باز کنند**؛ فقط با آگاهی از این اثر و ترجیحاً با حساب‌های آزمایشی روشن شود. شاگرد صفحهٔ برنامه را تازه می‌کند و «خرید و فعال‌سازی آزمایشی» را می‌زند؛ تأیید، خرید را ثبت و برنامه را موقتاً باز می‌کند و انصراف، آن را بسته نگه می‌دارد. هیچ صفحهٔ بانک یا انتقال پولی وجود ندارد.

در بخش مالی مربی و مدیر، «گزارش مالی آزمایشی» مبلغ، سهم‌ها و وضعیت موفق، در انتظار، لغوشده یا منقضی‌شده را نشان می‌دهد. سهم با تابع و تنظیم همان پرداخت واقعی در زمان شروع خرید محاسبه و ثبت می‌شود (پیش‌فرض ۹۰٪ مربی و ۱۰٪ باشگاه). فقط خرید موفق در جمع‌های آزمایشی حساب می‌شود؛ جدول‌های دسترسی و تراکنش آزمایشی (`payment_test_purchases` و `payment_test_transactions`) از `payment_transactions` جدا هستند و پرداخت، درآمد، تسویه و بایگانی خرید واقعی را تغییر نمی‌دهند. گزارش‌های آزمایشی پس از پایان مهلت، خاموش‌کردن حالت یا تنظیم درگاه باقی می‌مانند؛ وجود تراکنش واقعی یا آزمایشی مانع حذف حساب مرتبط می‌شود و غیرفعال‌سازی جایگزین حذف است. رکوردهای خرید آزمایشی قبل از اضافه‌شدن گزارش مالی، زمان و سهم ثبت‌شده ندارند و به‌طور حدسی بازسازی نمی‌شوند؛ برای دیدن گزارش جدید، دسترسی قبلی را خاتمه دهید و دوباره آزمایش کنید.

مربی یا مدیر همچنان می‌تواند به‌جای حالت سراسری، در برنامه‌ساز «خرید آزمایشی برای این شاگرد» را به‌طور فردی مجاز کند. پایان آزمایش سراسری مجوزهای فردی را لغو نمی‌کند؛ مربی باید آن‌ها را جداگانه ببندد. در زمان روشن‌بودن حالت سراسری، لغو مجوز فردی مانع شروع دوبارهٔ آزمایش آن شاگرد نمی‌شود. هر مجوز حداکثر ۲۴ ساعت اعتبار دارد؛ ویرایش همان برنامه دسترسی را تا پایان مهلت حفظ می‌کند و برنامهٔ جدید خرید جداگانه می‌خواهد. جلسات و اطلاعاتی که کاربر در طول آزمون ثبت کند، دادهٔ عادی حساب‌اند و خودکار پاک نمی‌شوند.

با تنظیم شناسهٔ پذیرندهٔ غیرخالی یا `STUDENT_TEST_PURCHASES=off|false|0` و راه‌اندازی مجدد سرور، خرید آزمایشی بسته و مجوزهای قبلی از جدول تست پاک می‌شوند؛ با حذف تنظیم دوباره زنده نمی‌شوند. پیش از انتشار از پایگاه داده پشتیبان بگیرید و از اجرای هم‌زمان نسخه‌ها یا تنظیمات متفاوت بین نمونه‌ها پرهیز کنید. لغو و انقضا دسترسی درخواست‌های بعدی سرور را قطع می‌کند؛ رابط هنگام تمرکز، تقریباً هر ۶۰ ثانیه و در پایان مهلت بازبررسی می‌کند، اما محتوای قبلاً دریافت‌شده یا ذخیره‌شده را نمی‌توان از دستگاه پس گرفت. حالت آفلاین و درخواست‌های از پیش شروع‌شده محدودیت دارند.

هیچ‌یک از این دو آزمایش callback، پرداخت بانکی یا تسهیم و تسویهٔ واقعی را تأیید نمی‌کند. خرید واقعی در production همچنان به شناسهٔ پذیرنده و `PAYMENT_PUBLIC_BASE_URL` معتبر نیاز دارد؛ اتصال، callback و تسویه باید جداگانه در محیط مناسب و با قرارداد درگاه آزموده شوند.

هر برنامه شناسهٔ مستقل دارد. «ویرایش برنامهٔ فعلی» همان خرید را حفظ می‌کند؛ «ثبت برنامهٔ جدید» شناسه و خرید مستقل می‌سازد. مربی متصل می‌تواند برنامهٔ سابق خودش را با همان شناسه دوباره فعال کند؛ خرید همان برنامه حفظ می‌شود و نسخهٔ کنترل هم‌زمان افزایش می‌یابد. شاگرد نسخه‌های قبلی خریداری‌شده یا رایگان را در بایگانی فقط برای مشاهده می‌بیند؛ شروع تمرین از برنامهٔ فعال است. ویرایش و حذف برنامه به شناسه و نسخه نیاز دارند و کلاینت قدیمی باید به‌روزرسانی شود. شروع پرداخت نیز شناسه و نسخهٔ نمایش‌داده‌شده را بررسی می‌کند. اگر برنامه پس از شروع پرداخت تغییر کند، پرداخت فقط به همان برنامه متصل است. پرداخت معلق دوباره استفاده می‌شود؛ اگر قیمت یا مربی عوض شده باشد، شروع مجدد به بررسی پشتیبانی نیاز دارد.

مهاجرت قدیمی یک‌بار دسترسی ناشی از تراکنش‌های پرداخت‌شدهٔ قبلی را به **برنامهٔ فعال همان شاگرد در زمان مهاجرت** نسبت می‌دهد، چون سوابق قدیم شناسهٔ برنامه نداشتند؛ این فرض همان دسترسی قبلی را حفظ می‌کند، ولی اثبات نمی‌کند تراکنش واقعاً برای همان برنامه بوده است. پرداخت معلق قدیمی فقط در صورت تطابق زمان، مبلغ و مربی به برنامهٔ فعال منتسب می‌شود. تراکنش‌های نامشخص در `payment_transactions` با `programme_id IS NULL` و `programme_mapping = 'legacy_unmapped'` باقی می‌مانند؛ باید پس از بررسی دستی و پشتیبان‌گیری رسیدگی شوند، نه اینکه دوباره از شاگرد پول گرفته شود. برنامه‌هایی که قبل از این نسخه جایگزین شده‌اند و نسخه‌ای از آن‌ها در پایگاه نداریم قابل بازسازی خودکار نیستند.

قبل از انتشار از PostgreSQL پشتیبان بگیرید و روی کپی داده، سوابق نامشخص و خریدهای فعال/در انتظار را با تیم مالی بررسی کنید. سرور قدیمی شناسهٔ خرید را نادیده می‌گیرد؛ استقرار مخلوط یا بازگشت به نسخهٔ قبلی می‌تواند برنامه‌های جدید را با پرداخت قبلی باز کند و باید با توقف فروش و طرح بازگشت هماهنگ انجام شود. از کارکرد بازپرداخت، لغو دیرهنگام و تسویهٔ واقعی در همهٔ حالت‌ها اطمینان حاصل نشده است؛ کد جای آزمون واقعی و بررسی قرارداد زرین‌پال را نمی‌گیرد.

### گوگل‌پلی و اشتراک آینده

این نسخه **Google Play Billing یا فروش اشتراک ندارد** و پوستهٔ فعلی اندروید در برنامه به پرداخت زرین‌پال هدایت می‌کند؛ نباید بدون بررسی سیاست انتشار همان فایل را آمادهٔ Google Play دانست. [جدول رسمی مناطق گوگل‌پلی](https://play.google.com/supported-locations?hl=en) برای ایران دریافت برنامهٔ رایگان را مجاز نشان می‌دهد، اما خرید درون‌برنامه‌ای و اشتراک Google Play را ناموجود نشان می‌دهد. کشور حساب Play کاربر با مکان فعلی او یکسان فرض نمی‌شود. [فهرست حساب‌های توسعه‌دهنده و فروشنده](https://support.google.com/googleplay/android-developer/answer/9306917) نیز ایران را در مناطق پشتیبانی‌شده ثبت‌نام فروشنده فهرست نمی‌کند. وضعیت حساب واقعی، مجوز انتشار، امکان دریافت پول و الزامات قانونی را با Google Play Console بررسی کنید.

[سیاست پرداخت گوگل](https://support.google.com/googleplay/android-developer/answer/9858738) برای کالاهای دیجیتال الزام‌ها و استثناهای وابسته به کشور دارد. گوگل در [راهنمای رسمی](https://support.google.com/googleplay/android-developer/answer/10281818) امکان نسخهٔ «صرفاً مصرف محتوا» را نیز توضیح می‌دهد، اما پیاده‌سازی و تأیید انطباق آن در این مخزن انجام نشده و مجوز هدایت به درگاه دیگر نیست.

اشتراک پیشنهادی می‌تواند امکانات پایش، تغذیه و برنامه‌های پیشنهادی را پوشش دهد و خرید برنامهٔ اختصاصی مربی را جدا نگه دارد؛ محدوده، قیمت و دوره هنوز تصمیم‌گیری و پیاده‌سازی نشده‌اند. در وضعیت فعلی بخشی از امکانات موسوم به هوش بر قواعد برنامه و داده‌های نمونه متکی است؛ تولید شخصی برنامه با مدل هوش مصنوعی، بازار و امتیازدهی مربیان، تأیید سروری اشتراک، تمدید، لغو و بازیابی خرید هنوز موجود نیستند. تا قبل از طراحی انتقال دسترسی، امکانات فعلی کاربران پشت اشتراک قرار نمی‌گیرند.

برای آمادگی Play، [سیاست دادهٔ کاربر](https://support.google.com/googleplay/android-developer/answer/10144311) به سیاست حریم خصوصی در اپ و صفحهٔ فروشگاه و در صورت شمول ساخت حساب به مسیر درخواست حذف حساب در اپ و وب نیاز دارد؛ غیرفعال‌سازی حساب جای حذف را نمی‌گیرد. در این مخزن مسیر کامل حذف دائمی حساب و داده‌های مرتبط یا سیاست جامع قابل انتشار مشاهده نشد؛ وضعیت URL بیرونی و Play Console بررسی نشده است. پیش از افزودن حذف، باید وابستگی‌های دادهٔ سه نقش، مهلت حذف، پشتیبان‌ها و نگهداری قانونی احتمالی تراکنش‌ها طراحی شوند. تکمیل دقیق Data safety و [اعلام قابلیت‌های سلامت](https://support.google.com/googleplay/android-developer/answer/14738291) در Play Console نیز باید بررسی شود.

### نصب مستقیم

مسیر فعلی معرفی مستقیم برنامه به مربیان و کاربران و استفاده از وب/PWA است. اشتراک مربی، پرداخت واقعی سهم‌ها و تسویهٔ خودکار هنوز پیاده‌سازی یا تأیید نشده‌اند.

برای نصب مستقیم از وب، [اندروید](https://developer.android.com/distribute/marketing-tools/alternative-distribution) دریافت APK امضاشده و اجازهٔ کاربر برای نصب از آن منبع را توضیح می‌دهد. برای ارتقای برنامهٔ نصب‌شده باید شناسهٔ بسته و امضای سازگار و شمارهٔ نسخهٔ مناسب حفظ شود؛ حذف و نصب دوباره ممکن است دادهٔ محلی همگام‌نشده را پاک کند. ساخت و امضای APK این مخزن، اتصال آن به سرور production و نصب/پرداخت روی دستگاه واقعی هنوز تأیید نشده است. نصب PWA از مرورگر بدون APK نیز بسته به مرورگر و دستگاه ممکن است؛ آن هم همان نسخهٔ مستقر روی سرور را نمایش می‌دهد، نه تغییرات صرفاً محلی.

## داده، حریم خصوصی و محدودیت‌های همگام‌سازی

- پروفایل، برنامهٔ شخصی، جلسات کامل، وزن، هدف‌ها و یادداشت روزانهٔ تغذیه، شاخص‌های سلامت، وضعیت مفاصل و یادداشت‌های خوراک با حسابِ واردشده روی PostgreSQL همگام می‌شوند. برنامهٔ اختصاص‌داده‌شده به شاگرد، دفتر خوراک، گفت‌وگو و تنظیمات مربی همچنان از APIهای مربوط به خودشان خوانده می‌شوند. خلاصهٔ حداکثر ۱۰۰ جلسهٔ اخیر شاگرد برای مربی از نسخهٔ کامل ساخته می‌شود.
- هر رکورد شخصی نسخه دارد؛ دستگاه پس از ذخیرهٔ محلی، هنگام اتصال، بازشدن/تمرکز صفحه و در فواصل تقریبی ۳۰ ثانیه نسخهٔ سرور را بررسی می‌کند. ویرایش هم‌زمان یا اختلاف دادهٔ قدیمی به جای رونویسی خاموش در «تنظیمات ← همگام‌سازی حساب» نمایش داده می‌شود؛ هر دو نسخه را بررسی و انتخاب کنید. حذف‌ها نیز نسخه‌دارند. پیش‌نویس ذخیره‌نشدهٔ فرم هنوز به سرور فرستاده نمی‌شود. همگام‌سازی در پس‌زمینهٔ بسته‌بودن برنامه تضمین نشده است.
- برنامه‌ساز مربی، برنامهٔ تمرینی شخصی، دفتر خوراک و برنامهٔ غذایی هفتگی، پیش‌نویس ذخیره‌نشده را در صورت اجازهٔ مرورگر برای بازیابی موقت در `sessionStorage` همان زبانه نگه می‌دارند. این نسخه به تفکیک حساب و در صورت نیاز شاگرد/روز است، سرور یا دستگاه دیگر را به‌روز نمی‌کند و پشتیبان دائمی نیست؛ با بستن زبانه، پاک‌سازی دادهٔ مرورگر یا محدودیت حافظه ممکن است از بین برود. هنگام تعارض، نسخهٔ تازه و پیش‌نویس باید بررسی و یکی صریحاً انتخاب شود. دادهٔ این حافظه رمزگذاری یا در برابر اسکریپت‌های همان مبدأ محافظت نشده است.
- کلاینت تازه هنگام ذخیرهٔ دفتر خوراک و برنامهٔ غذایی هفتگی، محتوای پایه را همراه درخواست می‌فرستد و سرور به‌صورت اتمیک محتوای موجود را با آن مقایسه می‌کند. اگر محتوای سرور فرق کند، ذخیرهٔ کهنه رد می‌شود. برای سازگاری، درخواست‌های کلاینت قدیمیِ فاقد پایه و شناسهٔ حساب هنوز پذیرفته می‌شوند و این محافظت را ندارند؛ همچنین بازگشت به سرور قدیمی یا پاسخ‌گرفتن موقت از آن حین استقرار، این محافظ را تضمین نمی‌کند. این تغییر schema دیتابیس را عوض نمی‌کند.
- نخستین بار پس از ورود، دریافت اطلاعات ممکن است کمی طول بکشد؛ وضعیت «همگام است» یا خطا را بررسی کنید. با قطع اینترنت، داده‌های ذخیره‌شده روی دستگاه می‌مانند و بعد از اتصال دوباره تلاش می‌شود. پاک‌کردن دادهٔ مرورگر پیش از تأیید همگام‌سازی، پیش‌نویس‌ها و تغییرات محلی ارسال‌نشده را از بین می‌برد. محدودیت هر رکورد ۲۰۰ کیلوبایت است؛ دادهٔ قدیمی نامعتبر یا بیش‌ازحد بزرگ به‌جای حذف در دستگاه باقی می‌ماند و خطا نمایش داده می‌شود.
- پایگاه محلی هر حساب جداست؛ خروج از حساب دادهٔ محلی را پاک نمی‌کند. این جداسازی رمزگذاری یا مرز امنیتی در برابر اسکریپت‌های همان مبدأ یا کسی با دسترسی به دستگاه نیست. توکن نشست برای سازگاری برخی محیط‌ها در `localStorage` نیز نگه‌داری می‌شود و در برابر XSS حفاظت `HttpOnly` ندارد. رمز ورود دیگر در برنامه ذخیره نمی‌شود و نسخهٔ plaintext باقی‌ماندهٔ قدیمی هنگام راه‌اندازی پاک می‌شود.
- **انتقال نسخهٔ قدیمی:** روی همان مرورگر و دستگاه قدیمی، وارد حساب شوید و در تنظیمات «انتقال دادهٔ قدیمی این دستگاه» را فقط پس از تأیید مالکیت بزنید. محدودهٔ قدیمی مدیر بین مدیران مشترک بود و نسخهٔ قدیمی برخی اطلاعات سلامت را بین حساب‌ها به‌اشتراک می‌گذاشت؛ برای شاگرد/مربی فقط گزینهٔ انتقال سلامت قدیمی وجود دارد. دادهٔ مبدأ حذف و مقصد موجود رونویسی نمی‌شود. پیش‌فرض‌های بسته‌بندی‌شدهٔ مدیر که قبلاً ممکن بود اصلاً در مرورگر ذخیره نشده باشند نیز فقط با همین تأیید وارد می‌شوند. اگر مقصد سرور متفاوت باشد باید تعارض را دستی بررسی کنید.
- پروفایل شاگرد با حساب خودش همگام می‌شود؛ دسترسی مربی نیازمند رضایت جداگانه است. هنگام نامشخص‌بودن وضعیت اشتراک، تغییر رضایت غیرفعال است اما ذخیرهٔ محلی پروفایل ممکن است. قطع اشتراک تنها پس از تأیید سرور مؤثر است؛ در صورت قطع اینترنت، برنامه هشدار می‌دهد که مربی ممکن است هنوز دسترسی داشته باشد. حذف نسخه‌دار پروفایل رضایت قبلی را لغو می‌کند.
- **هشدار مهم مخزن عمومی:** داده‌های پیش‌فرض قدیمی مالک در `src/data/profile.ts` و `src/data/adminProgram.ts` و در باندل کلاینت موجودند؛ این کد آن‌ها را دیگر خودکار به هر مدیر جدید نسبت نمی‌دهد، اما همگام‌سازی آن‌ها را از باندل یا تاریخچهٔ عمومی Git پاک نمی‌کند. مالک باید خصوصی‌بودن این موارد، دسترسی مخزن و در صورت لزوم پاک‌سازی تاریخچه را جداگانه بررسی کند. داده‌های سلامت در جداول سرور به‌شکل JSON ذخیره می‌شوند؛ رمزنگاری در سطح برنامه و سیاست پشتیبان/بازیابی یا دسترسی اپراتور دیتابیس در این تغییر تأمین نشده است.
- API قدیمیِ نوشتن بدون نسخه برای برنامهٔ شخصی اکنون خطای ۴۰۹ می‌دهد؛ پس از استقرار، مرورگرها و کلاینت‌های قدیمی باید به‌روزرسانی شوند. جدول جدید دادهٔ شخصی از برنامه و پروفایل قبلی سرور مقدار اولیه می‌گیرد و خلاصهٔ قدیمی جلسه فقط در نبود رکورد نسخه‌دار استفاده می‌شود. کامپوننت بلااستفادهٔ ارسال خلاصه از فرانت حذف شده، اما API و جدول قدیمی جلسات برای سازگاری و سوابق باقی مانده‌اند.
- خروجی JSON تنظیمات شامل پروفایل، هدف تغذیه، جلسه‌ها، وزن و یادداشت‌های محلی است؛ برنامه، گفتگو، دفتر خوراک سرور و همهٔ اطلاعات سلامت را پوشش نمی‌دهد و **بازیابی خودکار در برنامه ندارد**. فایل را محرمانه نگه دارید؛ برای دیتابیس سرور پشتیبان و آزمایش بازیابی مستقل لازم است.
- در صفحهٔ پیشرفت، جدول ست‌ها، جلسه‌ها و وزن‌ها به‌تدریج نمایش داده می‌شوند و با دکمهٔ «نمایش … دیگر» می‌توان به داده‌های قدیمی رسید. نمودارهای بزرگ با حفظ ابتدا/انتها و کمینه/بیشینهٔ بازه‌ها خلاصه می‌شوند؛ شمارش‌ها و سوابق از داده‌های کامل محاسبه می‌شوند.
- PWA بخشی از دارایی‌های رابط را cache می‌کند، اما همهٔ عملیات حساب‌دار/سرور و همهٔ تصاویر در حالت بی‌اتصال تضمین نشده‌اند. نسخهٔ تک‌فایل آفلاین حساب یا API ندارد و با سرور همگام نمی‌شود.

## ساخت امن اندروید

فایل APK قدیمی مخزن حذف شده است، چون با کد فعلی بازسازی و امضایش تأیید نشده بود. ساخت وب آن را خودکار منتشر نمی‌کند. تا وقتی APK جدید امضاشده و تأییدشده در نشانی قابل اعتماد قرار نگرفته، نصب وب در دسترس است و دکمهٔ دانلود APK غیرفعال می‌ماند.

گردش‌کار `.github/workflows/android-apk.yml` کلید جدید تولید نمی‌کند و بدون تنظیمات زیر شکست می‌خورد:

- متغیر مخزن `ANDROID_API_BASE`: مبدأ HTTPS عمومی API، بدون مسیر.
- رازهای GitHub Actions: `ANDROID_KEYSTORE_BASE64`، `ANDROID_KEYSTORE_PASSWORD`، `ANDROID_KEY_ALIAS` و `ANDROID_KEY_PASSWORD`؛ فایل keystore پایدار باید تحت کنترل مالک باشد و محتوای Base64 آن فقط در secret تنظیم شود.
- اجرای دستی یا push روی `main` خروجی امضاشده را به‌صورت artifact می‌سازد؛ push یک tag با پیشوند `v` پس از بررسی امضا آن را به GitHub Release همان tag اضافه می‌کند. گردش‌کار دیگر APK را خودکار به شاخه commit نمی‌کند. برای هر نسخه `versionCode`/`versionName` را طبق سیاست انتشار افزایش دهید.
- پس از ساخت، امضا و سازگاری را مستقل بررسی کنید و فقط بعد از انتشار فایل، `VITE_ANDROID_APK_URL` را برای ساخت وب تنظیم کنید. برای نشانی هم‌مبدأ `/meety.apk` می‌توان فایل تأییدشده را **بعد از build** در `dist/meety.apk` قرار داد؛ سرور دیگر به فایل قدیمی `public/` یا انتشار ثابت دیگری fallback نمی‌کند.

کلید قبلی اگر هنگام ساخت‌های پیشین خودکار تولید و نگه‌داری نشده باشد ممکن است در دسترس نباشد. یک کلید جدید به‌طور معمول قادر به به‌روزرسانی نصب امضاشده با کلید قبلی نیست. پیش از انتشار، امضای نسخهٔ نصب‌شده، کلید موجود و راهکار مهاجرت/پشتیبان دادهٔ کاربران را بررسی کنید؛ حذف نصب می‌تواند دادهٔ محلی را پاک کند. keystore یا رمزها را در Git قرار ندهید.

## ساختار

```text
src/             رابط، صفحات، ذخیره‌سازی محلی و منطق دامنه
server/          API، نشست‌ها، مجوزها، پرداخت و پایگاه داده
shared/          اعتبارسنجی‌های مشترک کلاینت و سرور
android/         پوستهٔ Capacitor و پیکربندی ساخت اندروید
tests/           آزمون‌های یکپارچهٔ رابط و منطق
tools/           ساخت و بررسی ساختاری بستهٔ آفلاین
```

از حرکات یا دامنه‌هایی که درد ایجاد می‌کنند صرف‌نظر کنید و در صورت نیاز از مربی یا متخصص واجد صلاحیت کمک بگیرید.
